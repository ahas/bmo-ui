# bmo-ui

基础 UI 库：设计令牌、组件库的覆盖配置，以及构成每个页面的通用组件和行为。它是一个构建在 Nuxt UI 之上的
Nuxt 层。

- **宿主通过 `extends` 引入它。** 该层带来 Nuxt UI 及其样式表、字体、覆盖配置、组件和页面插件；宿主则带来
  自己的模块、页面、地址和语言包。
- **它不显示任何自己的文字。** 每段文字都是一个由宿主语言包提供的键，读取日期所用的区域设置和时区也由宿主
  决定。
- **它不了解任何使用方，** 也不指名任何服务器：它只调用页面交给中继的服务和路径，以及控制台指定的翻译器。
  它对外暴露的内容和宿主应提供给它的内容，就是它的全部边界（`docs/boundary.md`）。
- **它规定了每个控制台包都遵循的控制台插件契约，** 因此控制台在运行时就能找到各个服务，并仅凭服务返回的
  清单挂载其包（`docs/console-bundles.md`）。
- **编码工具（harness）把它作为 MCP 服务器引入，** 即 `bmo-ui mcp`，一个包含其组件、令牌和契约的目录，旁边
  还有 `bmo-ui` 技能（`docs/harness.md`）。
- **它不依赖任何其他仓库，** 只依赖注册表中的包。
- **它不含任何个人数据。** 人名、邮件地址、主目录、设备或网络信息都应放在宿主的配置中，示例使用中性的名称；
  守卫测试会在每个文件中查找这类信息（`docs/PERSONAL-DATA.md`）。

## 使用方法

- 按原样 vendor `releases/` 中某个版本的文件，从该文件添加包，并在宿主的 Nuxt 配置中扩展它。已经 vendor
  过某个版本的宿主，可以用 vendor 命令切换到另一个版本（"Version"）。
- 在宿主中安装 `@nuxtjs/i18n`，并提供一个能回答边界文档所列全部键的语言包。该层将此模块及其引擎
  `vue-i18n` 声明为对等依赖。
- 将 `patches/` 中的补丁应用到宿主自身安装中的相同依赖上。
- 控制台在应用配置中写明中继的基础地址，如有翻译器则在运行时配置中指定其名称，并按契约挂载每个包。
- 编码工具从宿主的安装中启动 `bmo-ui mcp`，并加载 `skills/` 下的技能。

## 开发

- `bun install` 安装依赖并准备 Nuxt 的类型；由于包管理器的生命周期脚本运行时路径中没有本地二进制文件，
  prepare 步骤通过 `bun x` 调用本地的 Nuxt 命令行。
- `bun run release` 在 `releases/` 下写出清单版本的打包文件，并把它的 sha256 记入旁边的账本（"Version"）；
  这是产生打包文件的唯一途径。
- `bun run vendor <version> <checkout>...` 把已发布的文件放入每个检出目录下所有 vendor 了该层的清单中
  （"Version"）。
- `bun run elements` 把每个自定义元素构建为 `dist/` 下的单个脚本，git 会忽略该目录；打包时会先运行它，因此
  打包文件中包含这些脚本。
- `bun run typecheck` 连同组件示例一起检查该层、其测试以及编码工具插件的代码。
- `bun run catalogue` 从源码重新生成目录的数据文件；修改组件、令牌或边界文档时，该文件也应随之更新。
- `bun test <file>` 运行单个测试文件；`tests/browser/` 下的浏览器测试文件需逐个运行。
- `testbed.toml` 声明测试平台如何运行测试套件和快速检查。

## 目录结构

| 目录 | 内容 |
|---|---|
| `app/` | 该层的应用代码：`assets/` 下的样式表和附带许可证的字体，`components/` 下的组件，`domain/` 下的领域模块，`elements/` 下的自定义元素入口，`plugins/` 下的页面插件，包含库的覆盖配置和空的宿主设置的应用配置，以及借助宿主 i18n 模块为模板提供类型的声明 |
| `bin/` | 包的命令 |
| `bundle/` | 服务构建其控制台包时使用的包构建工具 |
| `catalogue/` | 目录模块及其数据文件、生成该文件的生成器，以及 `examples/` 下每个组件的示例 |
| `docs/` | 规范文档：设计基础、文案契约、组件、控制台插件契约、编码工具插件、个人数据规则和边界 |
| `mcp/` | 由命令启动的 MCP 服务器 |
| `patches/` | 安装时应用到依赖上的补丁 |
| `releases/` | 宿主引入的每个版本的打包文件，以及记录其 sha256 的账本 |
| `scripts/` | release 命令、vendor 命令，以及打包前先运行的检查 |
| `shared/` | 该层代码和宿主代码共同读取的共享模块 |
| `skills/` | `bmo-ui` 技能 |
| `tests/` | 测试；浏览器通道的文件及其辅助代码位于 `tests/browser/` 下 |

根目录下有包含版本和许可证的包清单及其锁文件、Nuxt 配置、自定义元素的构建配置、TypeScript 和 Bun 配置、
测试平台声明、快速检查读取的韩文账本、`CLAUDE.md`，以及 `LICENSE` 中的 MIT 许可证。

## 版本

- **整个仓库只有一个版本，** 也就是套件的版本：层与套件中所有单元处在同一版本，并依据 `docs/boundary.md`
  所规定的边界遵循语义化版本。版本从 git 标签读取，而不是从已提交的文件读取（bmo-chat 的
  `docs/conventions.md`「Versions」）；清单的版本和源码中的层版本是永不变动的占位值。
- **版本只在套件发布时变动。** 套件发布是所有者对整个套件的决定，它只给 main 所在的提交打上 `v<version>`
  标签，不做任何提交。套件中任何地方删除或改变了导出、prop、文案键或令牌即为主版本发布，新增即为次版本发布，
  只有修复则为补丁发布。
- **在发布标签所指的提交上做的打包，按该发布的版本打包：** alpha `X.Y.Z-alpha.<N>`、beta `X.Y.Z-beta.<N>`、
  候选版 `X.Y.Z-rc.<N>`、稳定版 `X.Y.Z` 或补丁。写入该文件是标签之后本仓库自己的提交，不属于发布本身。
- **其他打包文件都是当天的 nightly，** 命名为 `X.Y.Z-0.nightly.<YYYYMMDD>`：从提交所能到达的最新发布标签得出
  main 所通向的版本，再加上按平台时区（Asia/Seoul）计的打包日期。稳定版之后 main 通向上一级次版本，例如 `1.0.0`
  之后是 `1.1.0-0.nightly.20261124`；`X.Y.Z` 的 alpha 是最后一次发布时，通向 `X.Y.Z` 本身；`X.Y.Z` 的 beta
  或候选版是最后一次发布时，由于第一个 beta 已切出 `release/X.Y`，通向上一级次版本；没有任何发布标签时通向首次
  发布 `1.0.0`，主版本为 0 或带其他预发布词的标签（包括上游的标签）不算发布。同一天的第二次打包是 `1.1.0-0.nightly.20261124.2`，第三次是
  `.3`，依此类推。nightly 的名称只出现在打包文件之中，即其中打包的清单和层版本文件里，从不写入已提交的清单；
  语义化版本把每个 nightly 排在它之前的发布之后、它所通向版本的所有 alpha、beta、候选版和稳定版之前。以旧
  nightly 形式 `X.Y.Z-nightly.<YYYYMMDD>[.<n>]` 命名的打包保留原名，按现行形式中同一天的打包排序，并计入当天
  的打包。宿主仍按确切的名称和 sha256 固定打包，而不是按顺序。按旧编号方式产生的打包文件包含什么，由
  `docs/boundary.md` 说明。
- **一次打包就是一个打包文件，** 由 release 命令 `bun run release --bound <pack> --why <reason>` 写出一次，
  其中 `--bound this` 指正在制作的这次打包。已提交的树若正是其 `v<version>` 标签所指的提交，就按该发布的版本
  打包，否则按当天的 nightly 打包。该命令会拒绝：未指定下限（bound）或理由的打包；账本中在本次打包或更早没有
  记录的下限，或早于上一次打包下限的下限；按该顺序不排在账本中最后一个 nightly 之后的 nightly；有改动的工作树；以及已经存在文件或账本条目的名称。它把已提交的树
  导出到临时目录（`git archive`）并安装，在那里的清单中写入打包版本，在层版本文件中写入版本、下限以及从下限
  到本次的各次打包，以打包名称在 `releases/` 下打包一次，再把文件的 sha256、下限和理由追加到账本
  `releases/sha256.json`，并输出这三项。一次打包的文件永远不会被重写。
- **每次发布都会指明其下限：** 即其包在其上无需改动仍可运行的最早版本。只做新增的发布沿用之前的下限；删除或
  改变了旧包所读取内容的发布，则把下限提升为自身。控制台会挂载基于从其下限到自身版本之间任一版本构建的包
  （`docs/console-bundles.md`，"The layer a bundle is built on"）。
- **打包只在 release 命令内部运行。** 打包会先检查层的版本文件是否指向清单的版本，而这个文件只由该命令写入，
  因此在检出目录中运行 `bun pm pack` 会被拒绝。测试套件会核对 `releases/` 与其账本，因此不是由该命令写出的
  文件会导致失败。
- **文件包含** 清单的文件列表所列的内容：层的代码、样式表和字体、补丁、命令、MCP 服务器、包构建工具、目录
  模块及其数据文件、技能、Nuxt 配置、README、许可证和文档。
- **宿主按原样 vendor 该文件，** 并与账本核对，因此同一版本的所有宿主都基于相同的字节。宿主从不从源码打包该层，
  也不重命名或重新打包文件。
- **vendor 命令把宿主切换到某个版本，** 即 `bun run vendor <version> <checkout>...`；由于该命令在层的根目录
  运行，每个检出目录都以绝对路径指定。检出目录只由调用方提供，命令本身不知道任何宿主。它在每个检出目录下，用
  JSON 读取器读取依赖目录和隐藏目录之外的每个包清单，并选出那些在 dependencies、devDependencies 或
  optionalDependencies 中，`bmo-ui` 依赖是指向该检出目录内某个层打包文件的文件依赖的清单。对于每个指向其他
  版本的清单，它把该版本的文件从 `releases/` 复制到旧文件所在的目录，并与账本的 sha256 核对；按清单自身的写法
  把依赖指向新文件，把精确固定旧版本的对等依赖提升到新版本。每个值都用 JSON 编辑器原地修改，因此清单的其余
  字节保持仓库原有的格式（写在一行的数组仍保持一行）。随后删除旧文件，如果清单旁边或检出目录内的上级目录中有
  `bun.lock`，就用包管理器的 lockfile-only 安装重写锁文件。已经指向该版本的清单保持不变。它按检出目录输出每个
  清单中修改的内容，但不提交任何东西：由运行它的任务在各个仓库中提交。
  在做任何修改之前，它会拒绝以下情况并逐一指明：没有打包文件或账本条目的版本、字节与账本不符的文件、不是
  绝对路径或不是目录的检出路径、不含任何 vendor 了该层的清单的检出目录，以及位于检出目录之外的 vendor 文件。
- 指向检出目录的路径依赖，用于在改动等待发布期间支持仓库自身的工作和测试；以这种方式安装的层，其版本带有
  `+source` 标记，因此任何控制台都不会接受基于它构建的包。
