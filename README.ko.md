# bmo-ui

기반 UI 라이브러리입니다. 디자인 토큰, 컴포넌트 라이브러리 오버라이드, 그리고 모든 화면을 이루는 공통 컴포넌트와
동작을 담습니다. Nuxt UI 위에 세운 Nuxt 레이어입니다.

- **호스트는 `extends`로 이 레이어를 가져갑니다.** 레이어는 Nuxt UI와 그 스타일시트, 폰트, 오버라이드, 컴포넌트,
  페이지 플러그인을 가져오고, 호스트는 자신의 모듈, 페이지, 주소, 언어 팩을 가져옵니다.
- **자기 문구를 직접 보여 주지 않습니다.** 모든 문구는 호스트의 언어 팩이 답하는 키이며, 날짜를 읽는 로케일과
  시간대도 호스트가 정합니다.
- **소비자를 알지 못하며** 어떤 서버의 이름도 부르지 않습니다. 화면이 릴레이에 넘긴 서비스와 경로, 그리고 콘솔이
  지정한 번역기만 호출합니다. 레이어가 내보내는 것과 호스트가 레이어에 갖춰 줘야 하는 것이 경계의 전부입니다
  (`docs/boundary.md`).
- **모든 콘솔 번들이 따르는 콘솔 플러그인 계약을 정합니다.** 그래서 콘솔은 실행 중에 각 서비스를 찾고, 서비스가
  답하는 매니페스트만으로 번들을 붙입니다(`docs/console-bundles.md`).
- **코딩 하네스는 이 레이어를 MCP 서버로 가져갑니다.** `bmo-ui mcp`는 컴포넌트, 토큰, 계약의 카탈로그이며, 그
  옆에 `bmo-ui` 스킬이 있습니다(`docs/harness.md`).
- **다른 저장소에 의존하지 않고,** 레지스트리 패키지에만 의존합니다.
- **개인 정보를 담지 않습니다.** 사람의 이름, 메일 주소, 홈 폴더, 기기나 네트워크 정보는 호스트의 설정에 두고,
  예시에는 중립적인 이름을 씁니다. 가드 테스트가 모든 파일에서 이런 정보를 찾습니다(`docs/PERSONAL-DATA.md`).

## 사용하기

- `releases/`에 있는 릴리스 파일을 그대로 벤더링하고, 그 파일로 패키지를 추가한 뒤 호스트의 Nuxt 설정에서
  확장합니다. 이미 하나를 벤더링한 호스트는 vendor 명령으로 다른 릴리스로 옮깁니다("Version").
- 호스트에 `@nuxtjs/i18n`을 설치하고, 경계 문서가 나열하는 모든 키에 답하는 언어 팩을 줍니다. 레이어는 이
  모듈과 그 엔진인 `vue-i18n`을 피어 의존성으로 지정합니다.
- `patches/`의 패치를 호스트 자체 설치의 같은 의존성에 적용합니다.
- 콘솔은 앱 설정에 릴레이 기준 주소를 적고, 번역기가 있으면 런타임 설정에 그 이름을 적으며, 각 번들을 계약에
  따라 붙입니다.
- 하네스는 호스트의 설치에서 `bmo-ui mcp`를 실행하고 `skills/` 아래의 스킬을 불러옵니다.

## 개발하기

- `bun install`은 의존성을 설치하고 Nuxt의 타입을 준비합니다. 패키지 매니저의 라이프사이클은 로컬 바이너리를
  경로에 두지 않고 실행되므로, prepare 단계는 `bun x`를 거쳐 로컬 Nuxt 명령줄에 닿습니다.
- `bun run release`는 매니페스트 버전의 패킹 파일을 `releases/` 아래에 쓰고, 그 sha256을 옆의 원장에
  기록합니다("Version"). 패킹 파일이 생기는 길은 이것 하나뿐입니다.
- `bun run vendor <version> <checkout>...`은 각 체크아웃 아래에서 레이어를 벤더링하는 모든 매니페스트에
  릴리스 파일을 넣습니다("Version").
- `bun run elements`는 각 커스텀 엘리먼트를 `dist/` 아래의 스크립트 하나로 빌드하며, git은 이 폴더를
  무시합니다. 패킹이 이것을 먼저 실행하므로 패킹 파일에 스크립트가 들어갑니다.
- `bun run typecheck`는 레이어, 테스트, 하네스 플러그인 코드를 컴포넌트 예시와 함께 검사합니다.
- `bun run catalogue`는 소스로부터 카탈로그 데이터 파일을 다시 씁니다. 컴포넌트, 토큰, 경계 문서를 바꾸면
  이 파일도 함께 바뀝니다.
- `bun test <file>`은 테스트 파일 하나를 실행합니다. `tests/browser/` 아래의 브라우저 파일은 한 번에 하나씩
  실행합니다.
- `testbed.toml`은 테스트베드가 스위트와 빠른 검사를 실행하는 방법을 선언합니다.

## 구성

| 폴더 | 내용 |
|---|---|
| `app/` | 레이어의 앱 코드: `assets/` 아래의 스타일시트와 라이선스가 딸린 폰트, `components/` 아래의 컴포넌트, `domain/` 아래의 도메인 모듈, `elements/` 아래의 커스텀 엘리먼트 진입점, `plugins/` 아래의 페이지 플러그인, 라이브러리 오버라이드와 비어 있는 호스트 설정을 담은 앱 설정, 그리고 호스트의 i18n 모듈로 템플릿에 타입을 붙이는 선언 |
| `bin/` | 패키지의 명령 |
| `bundle/` | 서비스가 콘솔 번들을 빌드할 때 쓰는 번들 빌드 |
| `catalogue/` | 카탈로그 모듈과 데이터 파일, 그 파일을 쓰는 생성기, 그리고 `examples/` 아래의 모든 컴포넌트 예시 |
| `docs/` | 정본 문서: 디자인 기초, 문구 계약, 컴포넌트, 콘솔 플러그인 계약, 하네스 플러그인, 개인 정보 규칙, 경계 |
| `mcp/` | 명령이 시작하는 MCP 서버 |
| `patches/` | 설치할 때 의존성에 적용하는 패치 |
| `releases/` | 호스트가 가져가는 각 버전의 패킹 파일과 그 sha256 원장 |
| `scripts/` | release 명령, vendor 명령, 그리고 패킹이 먼저 실행하는 검사 |
| `shared/` | 레이어 코드와 호스트 코드가 함께 읽는 공유 모듈 |
| `skills/` | `bmo-ui` 스킬 |
| `tests/` | 테스트. 브라우저 레인의 파일과 그 지원 코드는 `tests/browser/` 아래에 있습니다 |

루트에는 버전과 라이선스를 담은 패키지 매니페스트와 그 잠금 파일, Nuxt 설정, 커스텀 엘리먼트 빌드 설정,
TypeScript와 Bun 설정, 테스트베드 선언, 빠른 검사가 읽는 한국어 원장, `CLAUDE.md`, 그리고 `LICENSE`의 MIT
라이선스가 있습니다.

## 버전

- **저장소 전체에 버전은 하나이며,** 매니페스트의 버전이고 곧 BMO 세트의 버전입니다. 레이어는 세트의 모든
  유닛이 서 있는 버전에 함께 섭니다(bmo-chat의 `docs/conventions.md`, "Versions"). `docs/boundary.md`가 정하는
  경계를 기준으로 시맨틱 버저닝을 따릅니다.
- **매니페스트의 버전은 세트 릴리스 때에만 움직입니다.** 세트 릴리스는 세트 전체에 대한 소유자의 결정이며,
  버전은 그 릴리스 커밋에서 바뀌고 그 커밋에는 `v<version>` 태그가 붙습니다. 세트 어디서든 export, prop,
  워딩 키, 토큰을 없애거나 바꾸면 메이저 릴리스, 추가하면 마이너 릴리스, 수정만 있으면 패치 릴리스입니다.
- **세트 릴리스 때마다 레이어는 세트의 버전으로 패킹됩니다.** 알파 `X.Y.Z-alpha.<N>`, 베타 `X.Y.Z-beta.<N>`,
  릴리스 후보 `X.Y.Z-rc.<N>`, 안정 릴리스 `X.Y.Z`, 패치가 그렇고, 그 `v<version>` 태그가 가리키는 커밋에서
  패킹됩니다.
- **릴리스 사이의 패킹 파일은 그날의 나이틀리입니다.** 이름은 `X.Y.Z-0.nightly.<YYYYMMDD>`로, 매니페스트의
  버전에서 main이 향하는 버전에 플랫폼 시간대(Asia/Seoul) 기준으로 패킹한 날짜를 붙입니다. main은 안정
  릴리스 다음에는 한 단계 위의 마이너로 향하고(예: `1.0.0` 다음은 `1.1.0-0.nightly.20261124`), `X.Y.Z`의
  알파가 마지막 릴리스인 동안에는 `X.Y.Z` 자신으로, `X.Y.Z`의 베타나 릴리스 후보가 마지막 릴리스인 동안에는 첫
  베타가 `release/X.Y`를 갈라 냈으므로 한 단계 위의 마이너로 향합니다. 세트의 첫 릴리스 전에는 `0.1.0`이나
  `0.1.0-rev.<n>` 리비전에서 세트의 첫 릴리스인 `1.0.0`으로 향합니다. 같은 날 두 번째 패킹은 `1.1.0-0.nightly.20261124.2`, 세
  번째는 `.3` 식으로 이어집니다. 나이틀리 이름은 패킹 파일 안, 곧 그 안에 패킹된 매니페스트와 레이어 버전
  파일에만 있고 커밋된 매니페스트에는 쓰이지 않습니다. 시맨틱 버저닝은 모든 나이틀리를 직전 릴리스 뒤, 그것이
  향하는 버전의 모든 알파, 베타, 릴리스 후보, 안정 릴리스 앞에 둡니다. 이전 나이틀리 형식
  `X.Y.Z-nightly.<YYYYMMDD>[.<n>]`으로 이름 붙은 패킹은 이름을 그대로 두며, 현재 형식의 같은 날 패킹으로
  정렬되고 그날의 패킹으로 셉니다. 호스트는 여전히 패킹을 순서가 아니라 정확한 이름과 sha256으로 고정합니다.
  이전 번호 체계의 패킹 파일이 무엇을 담는지는 `docs/boundary.md`가 밝힙니다.
- **패킹 하나는 패킹 파일 하나입니다.** 이 파일은 release 명령 `bun run release --bound <pack> --why
  <reason>`이 한 번만 쓰며, `--bound this`는 지금 만드는 패킹을 가리킵니다. 커밋된 트리가 `v<version>` 태그가
  가리키는 커밋이면 매니페스트의 버전으로, 그렇지 않으면 그날의 나이틀리로 패킹합니다. 이 명령은 하한(bound)이나
  이유를 적지 않은 패킹, 원장이 이 패킹 또는 그 이전에 기록하지 않은 하한이나 직전 패킹의 하한보다 이른 하한,
  그 순서로 원장의 마지막 나이틀리 뒤에 서지 않는 나이틀리, 변경 사항이 있는 작업 트리, 그리고 이미 파일이나 원장 줄이 있는 이름을 거부합니다. 명령은 커밋된 트리를 임시
  폴더로 내보내(`git archive`) 설치하고, 그곳의 매니페스트에 패킹 버전을, 레이어 버전 파일에 버전, 하한, 하한부터
  이번 패킹까지의 패킹 목록을 적은 뒤, 패킹 이름으로 `releases/` 아래에 한 번 패킹합니다. 그리고 파일의 sha256,
  하한, 이유를 원장 `releases/sha256.json`에 추가하며 세 가지를 모두 출력합니다. 한 패킹의 파일은 다시 쓰이지
  않습니다.
- **모든 릴리스는 자신의 하한을 밝힙니다.** 하한은 그 위에서 번들이 바뀌지 않고 그대로 실행되는 가장 오래된
  릴리스입니다. 추가만 하는 릴리스는 이전 하한을 유지하고, 이전 번들이 읽는 것을 없애거나 바꾸는 릴리스는
  하한을 자기 자신으로 올립니다. 콘솔은 하한부터 자신의 릴리스까지 어느 릴리스로 빌드한 번들이든
  붙입니다(`docs/console-bundles.md`, "The layer a bundle is built on").
- **패킹은 release 명령 안에서만 실행됩니다.** 패킹은 먼저 레이어의 버전 파일이 매니페스트의 버전을 가리키는지
  확인하는데, 이 파일은 release 명령만 쓰므로 체크아웃에서 `bun pm pack`을 실행하면 거부됩니다. 스위트는
  `releases/`와 그 원장을 서로 맞춰 보므로, release 명령이 쓰지 않은 파일이 있으면 실패합니다.
- **파일에는** 매니페스트의 파일 목록이 지정한 것이 담깁니다. 레이어 코드, 스타일시트와 폰트, 패치, 명령,
  MCP 서버, 번들 빌드, 카탈로그 모듈과 데이터 파일, 스킬, Nuxt 설정, README, 라이선스, 문서입니다.
- **호스트는 그 파일을 원장과 대조한 뒤 그대로 벤더링합니다.** 그래서 한 버전의 모든 호스트가 같은 바이트
  위에 섭니다. 호스트는 소스에서 레이어를 패킹하거나, 파일 이름을 바꾸거나, 다시 패킹하지 않습니다.
- **vendor 명령은 호스트를 릴리스로 옮깁니다.** `bun run vendor <version> <checkout>...`이며, 명령이 레이어의
  루트에서 실행되므로 각 체크아웃은 절대 경로로 지정합니다. 체크아웃은 호출자만 정하며, 명령은 어떤 호스트도
  알지 못합니다. 명령은 각 체크아웃 아래에서 의존성 폴더와 숨김 폴더 밖의 모든 패키지 매니페스트를 JSON
  리더로 읽고, dependencies, devDependencies, optionalDependencies 가운데 `bmo-ui` 의존성이 그 체크아웃 안에
  있는 레이어 패킹 파일을 가리키는 파일 의존성인 매니페스트를 고릅니다. 다른 릴리스를 가리키는 매니페스트마다
  버전 파일을 `releases/`에서 기존 파일이 있는 폴더로 복사하고 원장의 sha256과 대조합니다. 그런 다음
  매니페스트 자체의 표기로 의존성을 새 파일로 바꾸고, 이전 버전을 정확히 고정한 피어 의존성을 새 버전으로
  올립니다. 각 값은 JSON 편집기로 제자리에서 고치므로 매니페스트의 나머지 바이트는 저장소가 준 모양을 그대로
  유지합니다(한 줄짜리 배열은 한 줄로 남습니다). 이어서 기존 파일을 지우고, 매니페스트 옆이나 체크아웃 안의
  상위 폴더에 `bun.lock`이 있으면 패키지 매니저의 lockfile-only 설치로 잠금 파일을 다시 씁니다. 이미 그 버전을
  가리키는 매니페스트는 그대로 둡니다. 명령은 체크아웃별로 각 매니페스트에서 바꾼 내용을 출력하며, 아무것도
  커밋하지 않습니다. 커밋은 명령을 실행한 작업이 각 저장소에서 합니다.
  명령은 무엇이든 바꾸기 전에 패킹 파일이나 원장 줄이 없는 버전, 바이트가 원장과 맞지 않는 파일, 절대 경로가
  아니거나 폴더가 아닌 체크아웃 경로, 레이어를 벤더링하는 매니페스트가 없는 체크아웃, 체크아웃 밖에 있는
  벤더링 파일을 각각 이름을 밝혀 거부합니다.
- 체크아웃을 가리키는 경로 의존성은 변경이 릴리스를 기다리는 동안 저장소 자체의 작업과 테스트에 쓰입니다.
  이렇게 설치한 레이어는 버전에 `+source` 표시가 붙으므로, 어떤 콘솔도 그 위에서 빌드한 번들을 받지 않습니다.
