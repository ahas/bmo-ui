# bmo-ui

基盤となる UI ライブラリです。デザイントークン、コンポーネントライブラリのオーバーライド、そしてすべての画面を
構成する共通コンポーネントと振る舞いを提供します。Nuxt UI の上に構築した Nuxt レイヤーです。

- **ホストは `extends` でこのレイヤーを取り込みます。** レイヤーは Nuxt UI とそのスタイルシート、フォント、
  オーバーライド、コンポーネント、ページプラグインを持ち込み、ホストは自身のモジュール、ページ、アドレス、
  言語パックを持ち込みます。
- **独自の文言は一切表示しません。** すべての文言はホストの言語パックが答えるキーであり、日付を読むロケールと
  タイムゾーンもホストが決めます。
- **利用者を知らず、** どのサーバーも名指ししません。呼び出すのは、画面がリレーに渡したサービスとパス、そして
  コンソールが指定した翻訳器だけです。レイヤーが公開するものと、ホストがレイヤーに用意すべきものが境界の
  すべてです(`docs/boundary.md`)。
- **すべてのコンソールバンドルが従うコンソールプラグイン契約を定めます。** これによりコンソールは実行中に各
  サービスを見つけ、サービスが返すマニフェストだけを頼りにバンドルを組み込みます(`docs/console-bundles.md`)。
- **コーディングハーネスはこのレイヤーを MCP サーバーとして取り込みます。** `bmo-ui mcp` はコンポーネント、
  トークン、契約のカタログで、その隣に `bmo-ui` スキルがあります(`docs/harness.md`)。
- **他のリポジトリには依存せず、** レジストリのパッケージだけに依存します。
- **個人データを持ちません。** 人の名前、メールアドレス、ホームフォルダー、デバイスやネットワークの情報は
  ホストの設定に置き、例には中立的な名前を使います。ガードテストがすべてのファイルからそうした情報を探します
  (`docs/PERSONAL-DATA.md`)。

## 使い方

- `releases/` にあるリリースのファイルをそのままベンダリングし、そのファイルからパッケージを追加して、ホストの
  Nuxt 設定から拡張します。すでにベンダリングしているホストは、vendor コマンドで別のリリースに移します
  ("Version")。
- ホストに `@nuxtjs/i18n` をインストールし、境界ドキュメントが挙げるすべてのキーに答える言語パックを与えます。
  レイヤーはこのモジュールとそのエンジンである `vue-i18n` をピア依存として指定しています。
- `patches/` のパッチを、ホスト自身のインストールにある同じ依存関係に適用します。
- コンソールはアプリ設定にリレーのベースを記し、翻訳器がある場合はランタイム設定でその名前を指定し、各バンドルを
  契約に従って組み込みます。
- ハーネスはホストのインストールから `bmo-ui mcp` を起動し、`skills/` の下のスキルを読み込みます。

## 開発

- `bun install` は依存関係をインストールし、Nuxt の型を準備します。パッケージマネージャーのライフサイクルは
  ローカルのバイナリをパスに置かずに実行されるため、prepare ステップは `bun x` を通してローカルの Nuxt
  コマンドラインを呼び出します。
- `bun run release` はマニフェストのバージョンのパック済みファイルを `releases/` の下に書き出し、その sha256 を
  隣の台帳に記録します("Version")。パック済みファイルが生まれる手段はこれだけです。
- `bun run vendor <version> <checkout>...` は、各チェックアウトの下でレイヤーをベンダリングしているすべての
  マニフェストに、リリース済みのファイルを入れます("Version")。
- `bun run elements` は各カスタム要素を `dist/` の下の 1 本のスクリプトにビルドします。このフォルダーは git が
  無視します。パック時に先に実行されるため、パック済みファイルにはスクリプトが含まれます。
- `bun run typecheck` はレイヤー、テスト、ハーネスプラグインのコードを、コンポーネントの例とあわせて検査します。
- `bun run catalogue` はソースからカタログのデータファイルを書き直します。コンポーネント、トークン、境界
  ドキュメントを変更すると、このファイルも一緒に変わります。
- `bun test <file>` はテストファイルを 1 つ実行します。`tests/browser/` の下のブラウザー用ファイルは 1 つずつ
  実行します。
- `testbed.toml` は、テストベッドがスイートとクイックチェックをどう実行するかを宣言します。

## 構成

| フォルダー | 内容 |
|---|---|
| `app/` | レイヤーのアプリコード: `assets/` の下のスタイルシートとライセンス付きのフォント、`components/` の下のコンポーネント、`domain/` の下のドメインモジュール、`elements/` の下のカスタム要素のエントリー、`plugins/` の下のページプラグイン、ライブラリのオーバーライドと空のホスト設定を持つアプリ設定、そしてホストの i18n モジュールでテンプレートに型を付ける宣言 |
| `bin/` | パッケージのコマンド |
| `bundle/` | サービスがコンソールバンドルをビルドするためのバンドルビルド |
| `catalogue/` | カタログモジュールとデータファイル、そのファイルを書き出すジェネレーター、そして `examples/` の下にある全コンポーネントの例 |
| `docs/` | 正典となるドキュメント: デザインの基礎、文言の契約、コンポーネント、コンソールプラグイン契約、ハーネスプラグイン、個人データの規則、境界 |
| `mcp/` | コマンドが起動する MCP サーバー |
| `patches/` | インストール時に依存関係へ適用するパッチ |
| `releases/` | ホストが取り込む各バージョンのパック済みファイルと、その sha256 の台帳 |
| `scripts/` | release コマンド、vendor コマンド、そしてパック時に先に実行されるチェック |
| `shared/` | レイヤーのコードとホストのコードの双方が読む共有モジュール |
| `skills/` | `bmo-ui` スキル |
| `tests/` | テスト。ブラウザーレーンのファイルとその支援コードは `tests/browser/` の下にあります |

ルートには、バージョンとライセンスを持つパッケージマニフェストとそのロックファイル、Nuxt 設定、カスタム要素の
ビルド設定、TypeScript と Bun の設定、テストベッドの宣言、クイックチェックが読む韓国語台帳、`CLAUDE.md`、
そして `LICENSE` の MIT ライセンスがあります。

## バージョン

- **リポジトリ全体でバージョンは 1 つで、** セットのバージョンです。レイヤーはセットのすべてのユニットと同じ
  バージョンに立ち、`docs/boundary.md` が定める境界に対してセマンティックバージョニングに従います。バージョンは
  コミットされたファイルではなく git のタグから読み、マニフェストの
  バージョンとソースのレイヤーバージョンは動かないプレースホルダーです。
- **バージョンはセットのリリースでのみ動きます。** セットのリリースはセット全体に対するオーナーの決定で、main が
  立つコミットに `v<version>` タグを付けるだけで、何もコミットしません。セットのどこかで export、prop、文言キー、
  トークンを取り除くか変えればメジャー、追加ならマイナー、修正だけならパッチです。
- **リリースのタグが付いたコミットで作ったパックは、そのリリースのバージョンでパックされます。** アルファ
  `X.Y.Z-alpha.<N>`、ベータ `X.Y.Z-beta.<N>`、リリース候補 `X.Y.Z-rc.<N>`、安定版リリース `X.Y.Z`、パッチが
  それです。そのファイルを書くのはタグの後のこのリポジトリ自身のコミットで、リリースの一部ではありません。
- **それ以外のパック済みファイルはその日のナイトリーです。** 名前は `X.Y.Z-0.nightly.<YYYYMMDD>` で、
  コミットが届く最も新しいリリースタグから main が向かうバージョンに、プラットフォームのタイムゾーン(Asia/Seoul)でパック
  した日付を続けます。main は安定版リリースの後は 1 つ上のマイナーに向かい(たとえば `1.0.0` の次は
  `1.1.0-0.nightly.20261124`)、`X.Y.Z` のアルファが最後のリリースである間は `X.Y.Z` そのものに、`X.Y.Z` の
  ベータかリリース候補が最後である間は、最初のベータが `release/X.Y` を切り出しているので 1 つ上のマイナーに
  向かいます。リリースタグが 1 つもなければ最初のリリースである `1.0.0` に向かい、メジャー 0 や
  ほかのプレリリース語のタグ(アップストリームのものを含む)はリリースに数えません。同じ日の 2 回目のパックは `1.1.0-0.nightly.20261124.2`、3 回目は `.3` と続きます。ナイトリーの
  名前はパック済みファイルの中、つまりそこにパックされたマニフェストとレイヤーのバージョンファイルにだけあり、
  コミットされたマニフェストには書かれません。セマンティックバージョニングはすべてのナイトリーを直前のリリース
  の後、それが向かうバージョンのすべてのアルファ、ベータ、リリース候補、安定版リリースの前に並べます。以前の
  ナイトリー形式 `X.Y.Z-nightly.<YYYYMMDD>[.<n>]` で名付けられたパックは名前をそのまま保ち、現在の形式の同じ日
  のパックとして並べられ、その日のパックに数えられます。ホストは引き続き、パックを順序ではなく正確な名前と
  sha256 で固定します。以前の番号体系で作られたパック済みファイルが何を含むかは `docs/boundary.md` が示します。
- **1 つのパックは 1 つのパック済みファイルです。** release コマンド `bun run release --bound <pack> --why
  <reason>` が一度だけ書き出し、`--bound this` はいま作るパックを指します。コミット済みのツリーが
  `v<version>` タグの指すコミットならそのリリースのバージョンで、そうでなければその日のナイトリーでパックします。
  このコマンドは、下限(bound)や理由を指定しないパック、台帳がこのパック以前に記録していない下限や直前のパックの
  下限より古い下限、その順序で台帳の最後のナイトリーの後に来ないナイトリー、変更のある作業ツリー、そしてすでにファイルや台帳の行がある名前を拒否します。コマンドは
  コミット済みのツリーを一時フォルダーへエクスポートし(`git archive`)、インストールして、そこのマニフェストに
  パックのバージョンを、レイヤーのバージョンファイルにバージョン、下限、下限から今回までのパックを書き込み、
  パックの名前で `releases/` の下に一度だけパックします。そしてファイルの sha256、下限、理由を台帳
  `releases/sha256.json` に追加し、その 3 つをすべて表示します。あるパックのファイルが書き直されることは
  ありません。
- **すべてのリリースは自分の下限を示します。** 下限とは、その上でバンドルが変更なしにそのまま動く最も古い
  リリースです。追加だけのリリースは直前の下限を保ち、以前のバンドルが読むものを取り除いたり変えたりする
  リリースは下限を自分自身に引き上げます。コンソールは、下限から自分のリリースまでのどのリリースでビルドされた
  バンドルでも組み込みます(`docs/console-bundles.md`、"The layer a bundle is built on")。
- **パックは release コマンドの中でのみ実行されます。** パックはまず、レイヤーのバージョンファイルがマニフェストの
  バージョンを指しているかを確認します。このファイルを書くのは release コマンドだけなので、チェックアウトで
  `bun pm pack` を実行すると拒否されます。スイートは `releases/` とその台帳を突き合わせるため、release コマンドが
  書いていないファイルがあると失敗します。
- **ファイルに含まれるのは** マニフェストのファイルリストが指定するもの、つまりレイヤーのコード、スタイルシートと
  フォント、パッチ、コマンド、MCP サーバー、バンドルビルド、カタログモジュールとデータファイル、スキル、Nuxt
  設定、README、ライセンス、ドキュメントです。
- **ホストはそのファイルを台帳と照合したうえで、そのままベンダリングします。** そのため、あるバージョンのホストは
  すべて同じバイト列の上に立ちます。ホストがソースからレイヤーをパックしたり、ファイル名を変えたり、パックし
  直したりすることはありません。
- **vendor コマンドはホストをリリースへ移します。** `bun run vendor <version> <checkout>...` で、コマンドは
  レイヤーのルートから実行されるため、各チェックアウトは絶対パスで指定します。チェックアウトを決めるのは呼び出し
  側だけで、コマンドはどのホストも知りません。コマンドは各チェックアウトの下で、依存関係フォルダーと隠しフォルダー
  以外にあるすべてのパッケージマニフェストを JSON リーダーで読み、dependencies、devDependencies、
  optionalDependencies のうち `bmo-ui` 依存がそのチェックアウト内のレイヤーのパック済みファイルを指すファイル依存に
  なっているものを選びます。別のリリースを指しているマニフェストごとに、バージョンのファイルを `releases/` から
  古いファイルのあるフォルダーへコピーして台帳の sha256 と照合し、マニフェスト自身の書き方で依存を新しいファイルに
  向け、古いバージョンを厳密に固定しているピア依存を新しいバージョンに引き上げます。各値は JSON エディターで
  その場で編集するので、マニフェストの他のバイトはリポジトリが与えたレイアウトのまま保たれます(1 行の配列は
  1 行のまま残ります)。続いて古いファイルを削除し、マニフェストの隣かチェックアウト内の上位フォルダーに
  `bun.lock` があれば、パッケージマネージャーの lockfile-only インストールでロックファイルを書き直します。すでに
  そのバージョンを指すマニフェストはそのままにします。コマンドはチェックアウトごとに各マニフェストで変えた内容を
  表示し、何もコミットしません。コミットするのは、コマンドを実行したジョブが各リポジトリで行います。
  何かを変える前に、コマンドはパック済みファイルや台帳の行がないバージョン、バイト列が台帳と一致しない
  ファイル、絶対パスでないかフォルダーでないチェックアウトのパス、レイヤーをベンダリングするマニフェストを
  持たないチェックアウト、そしてチェックアウトの外にあるベンダリング済みファイルを、それぞれ名前を挙げて拒否
  します。
- チェックアウトへのパス依存は、変更がリリースを待つ間、リポジトリ自身の作業とテストに使われます。これで
  インストールしたレイヤーはバージョンに `+source` の印が付くため、どのコンソールもその上でビルドされたバンドルを
  受け付けません。
